# Frontend MIS Dash

`src/app` — тонкий Streamlit-слой над `DashboardResponse 1.1`. Он отвечает за
выбор источника JSON, композицию экранов и состояние интерфейса, но не разбирает
поля исходной МИС и не вычисляет медицинские показатели.

Интерфейс использует медицинскую светлую тему, согласованную с презентацией
проекта: холодный фон, тёмно-синий структурный цвет, голубой и бирюзовый для
данных, янтарный для предупреждений и красный только для критических сигналов.

## Запуск

Из корня репозитория:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
streamlit run src/app/main.py
```

`GEMINI_API_KEY` нужен только для ИИ-сводки: без него профиль, графики и приёмы
продолжают работать. `OUTPUT_DIR` относится к файловому методу
`MISParser.parse()` и не меняет Streamlit: выбранная выгрузка обрабатывается
через `parse_record()` в памяти. Реальные ключи и медицинские данные нельзя
добавлять в Git.

## Выбор источника

Панель источника находится в sidebar, чтобы технические controls не занимали
основной демонстрационный кадр. Переключатель предлагает два сценария:

- **Загрузить JSON** — передать существующую выгрузку;
- **Сгенерировать синтетическую выгрузку** — указать `seed`, глубину истории
  от 1 до 9 лет и режим сокращённых приёмов и исследований.

Generator вызывается только после кнопки формы, а не при каждом rerun. Значения
по умолчанию — `seed=7`, три года и включённый `light`. Этот режим уменьшает
число приёмов, лабораторных заказов и инструментальных исследований, но не
плотность дневников самоконтроля. Созданный JSON хранится в
`st.session_state`, повторно используется при переключении элементов
интерфейса и доступен для скачивания.

Кнопка «Случайный seed» только подставляет новое целое значение в поле. Она не
создаёт пациента и не заменяет текущую выгрузку до нажатия
«Сгенерировать и открыть».

После успешной обработки имя готового файла показывается компактным статусом в
sidebar. Рабочая область начинается сразу с навигации дашборда; постоянные
служебные подтверждения над содержимым не выводятся.

## Поток данных

```text
Загруженный JSON ─────────────┐
                             ├─> JSON bytes
Форма -> src/generator ───────┘
    -> src/app/data.py: build_pipeline()
    -> MISParser
    -> PatientRecord 1.0
    -> DashboardService
    -> DashboardResponse 1.1
    -> компоненты Streamlit
```

`source.py` приводит оба сценария к одному `PatientInput` с JSON-байтами,
именем файла и признаком происхождения. `data.py` сохраняет байты во временный
файл только на время вызова parser и удаляет его в `finally`. Один кешируемый
`build_pipeline()` строит и `PatientRecord`, и `DashboardResponse`, поэтому
parser/backend не запускаются повторно для одного содержимого. Кеш ограничен
четырьмя входами.

Детерминированные компоненты получают Pydantic-модель `DashboardResponse`,
поэтому не зависят от имён ключей в грязном JSON. Только orchestration-код
ИИ-сводки дополнительно получает `PatientRecord`, чтобы выбрать свободный
текст. Синтетический файл не получает привилегированного пути: он проходит тот
же `MISParser`, что и загруженный.

## Структура модуля

- `main.py` — тонкая точка входа и обработка состояния загрузки;
- `dashboard.py` — верхняя навигация и ленивый выбор одного раздела;
- `theme.py` — единые design tokens, CSS, заголовки и пустые состояния;
- `source.py` — переключатель загрузки/generator, форма и исходный JSON;
- `data.py` — общая граница между JSON-байтами, parser и backend;
- `summary.py` — явный запуск Gemini и кеширование результата в сессии;
- `components/patient.py` — профиль, аллергии, диагнозы и терапия;
- `components/metrics.py` — вкладки и Plotly-графики;
- `components/visits.py` — таблица врачебных приёмов;
- `components/insights.py` — красные флаги и готовая ИИ-сводка.

Настройки базовой светлой темы находятся в `.streamlit/config.toml`. Все
дополнительные стили централизованы в `theme.py`; компоненты не вставляют
собственные несогласованные блоки `<style>`.

## Навигация и первый экран

После обработки файла отображается переключатель четырёх взаимоисключающих
разделов:

- **Обзор** — идентификация пациента, пять ключевых фактов, красные флаги,
  затем аллергии, диагнозы и терапия;
- **Динамика** — только активная группа временных рядов;
- **Приёмы** — поиск и таблица хронологии;
- **ИИ-сводка** — явная кнопка Gemini и сохранённый результат.

В каждый момент рендерится только выбранный раздел. Это уменьшает высоту
страницы, не создаёт скрытые Plotly-графики и не вызывает Gemini при обычном
переключении навигации. На первом экране клинические сигналы расположены сразу
после компактной шапки; подробный клинический контекст идёт ниже.

Раздел **Приёмы** использует собственную компактную HTML-таблицу со sticky
заголовком и вертикальной прокруткой. Врач и специальность объединены в одной
ячейке. Основной диагноз показан полностью, до четырёх сопутствующих диагнозов —
кодами-плашками, остальные доступны через индикатор количества и tooltip.
Поиск учитывает полный, в том числе скрытый, список диагнозов. Длинные жалобы
ограничены тремя строками, а полный текст доступен в tooltip.

## Мобильное отображение

При ширине до `720px` боковая панель первоначально свёрнута, а основная
навигация перестраивается в сетку 2×2 с touch-областями не менее 44 px.
Паспорт пациента и карточки последних значений используют двухколоночную
сетку; клинические панели и красные флаги располагаются последовательно.
Вкладки групп метрик прокручиваются горизонтально.

Легенда графика рендерится вне canvas Plotly и на телефоне перестраивается в
одну колонку, поэтому длинные названия серий не перекрывают друг друга.
Таблица приёмов превращается в вертикальный список карточек: дата и врач
остаются в первой строке, диагнозы и жалобы занимают полную ширину. Для неё не
требуется горизонтальная прокрутка.

## Группы показателей

Frontend группирует стабильные backend-коды только для навигации. Название
вкладки не является диагнозом и не меняет контракт данных.
Над графиками активной группы расположен один общий ползунок периода. Он
синхронно задаёт диапазон дат для всех графиков группы, включая показатели с
разными единицами измерения. Названия серий и единицы выводятся в карточках
актуальных значений и легенде, поэтому подписи осей не дублируют их.

| Вкладка | Коды временных рядов |
| --- | --- |
| Артериальное давление | `systolic`, `diastolic`, `pulse-pressure` |
| Гликемический контроль | `glucose`, `hba1c` |
| Почки | `creatinine`, `egfr-ckd-epi-2021`, `urine-albumin-creatinine-ratio`, `potassium` |
| Липиды | `total-cholesterol`, `non-hdl-cholesterol`, `ldl-cholesterol`, `calculated-ldl-cholesterol`, `hdl-cholesterol`, `triglycerides` |
| Вес и BMI | `body-weight`, `bmi` |

Показываются только вкладки, для которых есть непустые ряды. Внутри группы
показатели с одинаковой единицей попадают на один график, а с разными единицами
— на отдельные. Рендерится только открытая вкладка: это уменьшает число
одновременно созданных Plotly-графиков и предотвращает сбои плотной страницы.
Для длинных рядов маркеры скрываются, а начальный диапазон ограничивается
последними 90 днями; для остальных длинных историй — последним годом.

Перед графиком показываются карточки последних значений с датой. Расчётные
показатели выводятся первыми, имеют отдельную метку и выделенный фон карточки.
На графике их линии толще, а точки имеют ромбовидный маркер. Plotly использует
фиксированные цвета серий из палитры приложения, белый фон, спокойную сетку,
единый hover и короткий transition. `theme=None` не позволяет теме Streamlit
переопределять эти настройки.

Backend также умеет публиковать `heart-rate`, `oxygen-saturation` и
`body-temperature`, но в текущий allowlist `METRIC_GROUPS` они не входят и
отдельных вкладок для них нет. Добавление ряда в backend само по себе поэтому
не создаёт новый график.

Производные показатели визуально помечаются как расчётные. Под графиками
frontend универсально отображает переданный backend-блок `calculation`: что это
за показатель, какие данные использованы, для чего он нужен, метод, основание,
ограничения и ссылки. Если backend передал категорию значения (`G*` или `A*`),
она показывается во всплывающей подсказке точки. Формулы и медицинские пояснения
не зашиты в Streamlit.

В том же раскрывающемся блоке показывается демонстрация последней доступной
расчётной точки: дата, фактические операнды, единицы, ID исходных наблюдений,
результат и категория. Данные приходят в `calculation_inputs` схемы
`DashboardResponse 1.1`; frontend только форматирует их и не повторяет
вычисления.

## ИИ-сводка и состояние сессии

Gemini вызывается только по кнопке. Результат хранится в `st.session_state` по
хешу файла, модели и версии промпта, поэтому обычный rerun или переключение
вкладок не расходуют квоту повторно. Новый файл получает другой ключ и не видит
сводку предыдущего пациента. Ошибка API отображается предупреждением и не
прерывает остальной дашборд. Подробности контракта описаны в
[документации summarizer](summarizer.md).

## Красные флаги

`components/insights.py` не содержит медицинских порогов. Он читает готовые
`dashboard.red_flags`, показывает заголовок и первое предложение как короткую
карточку, а оставшееся обоснование — в раскрываемом блоке «Почему сработало
правило». Уровни `critical`, `warning` и `info` отличаются цветом и текстовой
меткой, поэтому смысл не зависит только от цвета. Значения, даты и ограничения
формирует backend rules engine; его правила описаны в
[документации красных флагов](red_flags.md).

## Анимации и доступность

Анимации используются только для появления крупных секций и hover-состояний:
`opacity` и вертикальный сдвиг выполняются примерно за 300 ms. Plotly получает
короткий transition, но тысячи точек не анимируются по отдельности. Бесконечных
пульсаций и мигания у красных флагов нет.

Медиа-запрос `prefers-reduced-motion: reduce` полностью отключает CSS-анимации
и transitions. Контрастные оттенки для мелкого текста темнее декоративных
акцентов слайда. Все значения, переданные в собственную HTML-разметку,
экранируются.

## Скриншоты для презентации

В `docs/screenshots/` лежат воспроизводимые кадры синтетической конфигурации
`seed=7`, `years=3`, `light=true`. Рекомендуемый viewport — `1600×900`;
браузер должен иметь масштаб 100%.

- `dashboard-overview.png` — компактная шапка и клинические сигналы;
- `dashboard-metrics.png` — карточки последних значений и график АД;
- `dashboard-visits.png` — поиск и хронология приёмов.

Перед обновлением снимков нужно запустить приложение заново, выбрать ту же
конфигурацию, дождаться окончания обработки и проверить, что на кадре нет
реальных данных или секретов. Скриншот Overview снимается с начала раздела,
Dynamics и Visits — от заголовка выбранного раздела.

## Проверка изменений

```bash
pytest -q tests/test_app_data.py tests/test_app_source.py \
  tests/test_app_dashboard.py tests/test_app_theme.py \
  tests/test_app_metrics.py \
  tests/test_app_insights.py tests/test_app_patient.py \
  tests/test_app_summary.py tests/test_app_visits.py
pytest -q
```

При добавлении временного ряда сначала опубликуйте стабильный код в backend,
затем включите его в подходящую `MetricGroup` и обновите таблицу выше и тесты.
Новый компонент должен принимать `DashboardResponse` или его типизированную
часть, а не словарь исходной выгрузки.

## Заметки по развитию frontend

- аутентификация и production deployment не реализованы;
- `st.cache_data` и session state рассчитаны на синтетический прототип; для
  реальных медицинских данных понадобятся аутентификация, изоляция пользователей
  и отдельная политика хранения;
- перед релизом нужно проверить интерфейс на нескольких конфигурациях
  встроенного generator и на узком экране;
- решения о новых вкладках, состояниях и ограничениях frontend следует
  фиксировать в этом разделе вместе с изменением кода.
