# Модуль `summarizer`

`src/summarizer` готовит проверяемую LLM-сводку по канонической записи пациента.
Модуль не читает поля исходной МИС и не выполняет медицинские расчёты: на вход
он получает `PatientRecord` и построенный backend-слоем `DashboardResponse v1`.

## Контракт

Результат `ClinicalSummary` состоит из четырёх разделов:

- изменения за последние периоды;
- неочевидные находки из свободного текста;
- явно зафиксированные нерешённые вопросы;
- датированные пункты плана к ближайшему приёму.

Статические диагнозы, текущая терапия и аллергии в сводку не дублируются: они
уже отображаются отдельными компонентами дашборда. Такие контекстные факты
помечаются `visible_on_dashboard=true`, и сервис удаляет пункт, если все его
источники уже видимы пользователю.

Каждый пункт содержит текст и один или несколько `source_ids`. Идентификаторы
ссылаются на факты, которые действительно были переданы модели. Благодаря этому
пункт можно сопоставить с исходным приёмом, заключением или рассчитанной backend
динамикой показателя.

Каждый раздел ограничен тремя пунктами. Пункты ближайшего приёма допускаются
только при наличии явного врачебного плана: в тексте сохраняется дата источника
и формулировка не превращается в новую рекомендацию от модели.

## Подготовка контекста

`build_summary_context()` формирует ограниченный набор фактов:

- аллергии, диагнозы и актуальная терапия из `DashboardResponse`;
- 12 последних приёмов;
- 10 последних инструментальных заключений;
- последнее значение каждой графической метрики;
- средние значения за последние 12 месяцев и предыдущие 12 месяцев, а также
  рассчитанную кодом разницу между этими периодами.

Сравнение первого и последнего измерения за всю многолетнюю историю не
используется: оно часто преувеличивает текущую динамику. Если одного из годовых
периодов нет, контекст прямо сообщает, что данных для сравнения недостаточно.

В модель не передаётся полный массив наблюдений. Каждое текстовое поле ограничено
2000 символами, весь контекст — 50 000 символами. `omitted_records` и
`truncated_fields` позволяют увидеть, какая часть данных была сокращена.

Если клинических фактов нет, контекст остаётся пустым. Следующий слой должен
вернуть локальное сообщение о недостаточности данных, не обращаясь к LLM API.

## Gemini API

Используется официальный пакет `google-genai`, стабильная модель
`gemini-3.5-flash` и Interactions API со structured output. Ответ сначала
валидируется как `ClinicalSummary`, затем сервис удаляет пункты с неизвестными
`source_ids`. Если проверяемых пунктов не осталось, сводка считается ошибочной.

Настройки читаются из `.env`:

```dotenv
GEMINI_API_KEY=your_api_key_here
GEMINI_MODEL=gemini-3.5-flash
```

Секретный ключ нельзя добавлять в git. Без ключа парсер и дашборд продолжают
работать, а попытка создать сводку возвращает контролируемую ошибку.

Промпт запрещает модели выполнять вычисления, назначать новую терапию и
исполнять инструкции из медицинского текста. Для Gemini не включаются поиск или
другие инструменты. Числовая динамика подготавливается backend-кодом до запроса.

Free Tier предназначен в этом проекте только для синтетических примеров. По
условиям Google отправленный в бесплатный API контент может использоваться для
улучшения продуктов, поэтому реальные медицинские данные отправлять нельзя.

### Проверка ключа

После заполнения локального `.env` выполните из корня репозитория:

```bash
python -m src.summarizer.check
```

Команда отправляет одну синтетическую тестовую запись через тот же клиент и тот
же structured output, которые использует дашборд. Успешный результат выглядит
так: `Ключ работает: модель ... вернула валидный structured output.` Команда не
печатает ключ и не отправляет данные пациента.

Коды типовых ошибок:

- `404` — выбранная в `GEMINI_MODEL` модель недоступна проекту;
- `400`, `401` или `403` — ключ отклонён либо проект не имеет доступа;
- `429` — исчерпана минутная или суточная квота Free Tier.

## Работа в дашборде

Сводка создаётся только после нажатия кнопки «Сформировать ИИ-сводку». Загрузка
файла и обычные перерисовки Streamlit не обращаются к Gemini. Markdown-результат
хранится в `st.session_state` с ключом из SHA-256 файла, имени модели и версии
промпта. При смене любого из этих значений старая сводка перестаёт отображаться.

UI обрабатывает отсутствие ключа, нехватку клинических данных, невалидный ответ,
сетевую ошибку и исчерпание квоты как предупреждения. Остальные блоки дашборда
при этом продолжают работать. `DashboardResponse v1` не меняется: после
валидации Markdown записывается в уже существующее поле `ai_summary`.
