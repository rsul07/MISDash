# Техническое задание: MIS Dash — дашборд-сводка по данным медицинской информационной системы

> **Статус документа:** это исходная постановка учебного проекта. Она сохраняет
> первоначальные цели, примеры и Definition of Done, поэтому может описывать ещё
> не реализованные функции. Текущее состояние и фактические контракты смотрите
> в [индексе документации](README.md) и
> [архитектуре](architecture.md).

## 1. Зачем этот проект
В каждой российской поликлинике и больнице работает МИС — медицинская информационная система. В ней хранится вся история пациента: приемы врачей, анализы, диагнозы, операции, аллергии, вредные привычки. Проблема: когда врач открывает карту пациента с 9-летней историей, перед ним сотни записей, и на прием отведено 12–15 минут. Нужен инструмент, который за секунды показывает главное.

Мы делаем прототип такого инструмента. На вход — выгрузка из МИС: один огромный JSON-файл (~250 тысяч строк) со всей историей пациента. На выходе — веб-дашборд: сводка по пациенту, графики динамики анализов, «умные» флаги (тревожные значки) и краткое резюме истории болезни, сгенерированное LLM.

Проект учебный, данные синтетические (пациент выдуман, персональных данных нет), но структура и «кривизна» данных максимально приближены к реальным выгрузкам МИС. Все, чему вы научитесь, равно то, что делают инженеры в настоящих проектах медицинского ИИ.

## 2. Исходные данные
Вам выдаются: файл `patient_etalon.json` (~250 тыс. строк, полная 9-летняя история пациента), файл `patient_small_example.json` (уменьшенная версия для отладки) и скрипт-генератор, которым можно создавать новые примеры.

### Что внутри JSON (основные блоки):
* **PATIENT_INFO** — паспортная часть: ФИО, дата рождения, рост/вес, полис и т.д.
* **social_anamnez** — вредные привычки (курение с индексом пачка/лет), аллергии, семейный анамнез.
* **hron_zabolevaniya** — хронические диагнозы с кодами МКБ-10.
* **perenesennye_operacii, gospitalizacii, privivki** — операции, госпитализации, прививки.
* **PRIEMY_VRACHA** — протоколы приемов: жалобы, анамнез, объективный статус (свободный текст), измерения, диагнозы, назначения терапии.
* **lab_issledovaniya** — лабораторные анализы: панели (ОАК, биохимия, липидограмма, HbA1c...), значения, единицы, референсные диапазоны, флаги H/L.
* **instrumental_issled** — ЭКГ, ЭхоКГ, УЗИ, СМАД — заключения свободным текстом.
* **dnevnik_samokontrolya** — тегированная информация: АД и глюкоза из мобильного приложения пациента.
* **EHR_EVENT_LOG, legacy_import_v3, sluzhebnoe** — служебные и «мусорные» блоки: лог-журнал событий, частичный дубль данных после миграции со старой версии МИС... Их нужно распознать и обработать (или обоснованно исключить).

> **Важно:** данные намеренно «грязные», как в жизни. Имена полей — кривой транслит с опечатками (`birtf_date`, `JALOBY_TXT`). Даты в пяти форматах, включая unix-время строкой. Числа — то числом, то строкой с запятой (`"46,5"`). Пропуски — то null, то `"-"`, то «нет данных». Встречаются дубликаты записей. Разбираться с этим — половина сути проекта.

## 3. Что должно получиться
Веб-дашборд, который по загруженному JSON показывает:
* **Шапку пациента:** ФИО, возраст, ИМТ, группа крови, аллергии (крупно и заметно!), список хронических диагнозов, текущая терапия.
* **Графики динамики ключевых показателей по годам:** креатинин + расчетная СКФ, HbA1c и глюкоза, липиды, вес, АД (из протоколов и из дневника самоконтроля).
* **Ленту приемов:** дата, специалист, диагноз, кратко жалобы.
* **Панель красных флагов:** список сработавших правил и калькуляторов с объяснением, почему это флаг.
* **Блок «Резюме от ИИ»:** краткая LLM-сводка истории болезни и динамики состояния.

Дашборд должен работать не только на эталонном файле, но и на других файлах от генератора — не «хардкодим» под одного пациента.

## 4. Блоки работ

| Блок | Что делаем | Чему учимся |
| :--- | :--- | :--- |
| **0. Разведка данных** | Открываем JSON, строим карту его структуры: какие блоки есть, сколько записей, какие поля за что отвечают. Пишем скрипт-«описантизатор», который печатает дерево ключей и статистику. Составляем словарь соответствий: кривое имя поля -> человеческое название. | Python-словари/списки, работа с большим файлами, исследовательский анализ неименованных данных. |
| **1. Парсинг и нормализация** | Пишем парсер: приводим даты (5+ форматов) к одному виду, числа-строки с запятыми — к float, обрабатываем null/«нет данных»/«-», вычищаем явные дубликаты (приёмы, аллергии, legacy-блок). На выходе — чистые структуры данных (dataclasses или pydantic-модели). | Регулярные выражения, обработка граничных случаев, валидация данных, типизация. |
| **2. Извлечение из текста** | Из свободного текста протоколов регулярными вытяжками АД («АД 150/90»), ЧСС, ИМТ, дозировки препаратов. Сравниваем с полями измерителя — они не всегда совпадают, рискуем, чему верить. | Продвинутые regex (группы, альтернативы), работа с «грязным» текстом. |
| **3. Мед. калькуляторы и red flags** | Реализуем простые калькуляторы: ИМТ, СКФ (CKD-EPI), пачка/лет, среднее АД по дневнику. Задаём правила красных флагов: калий > 5.5, HbA1c > 8, СКФ < 45, ЛПНП выше цели, АД-кризы, «пациент 2 года не был у офтальмолога» и т.п. | Перевод формул из статьи в код, юнит-тесты на формулы, доменная логика. |
| **4. LLM-суммаризация** | Свободный текст (жалобы, анамнез, заключения УЗИ/экг) суммаризируем через LLM API: краткое резюме пациента, динамика состояния, «что изменилось с прошлого приёма». Учимся писать промты, запрашивать структурированный (JSON) ответ, обрабатывать ошибки и галлюцинации. | Работа с LLM API, промпт-инжиниринг, structured output, валидация ответов модели. |
| **5. Дашборд** | Собираем всё в веб-дашборд (Streamlit / Dash / plotly): шапка пациента, графики динамики (креатинин, HbA1c, вес, АД по дневнику), таблица приёмов, панель красных флагов, блок LLM-сводки. | Визуализация, продуктовое мышление: что врачу нужно видеть за 30 секунд. |
| **6\*. ML (по желанию)** | Если останется время: прогноз тренда показателя (линейная регрессия по хрупкости/HbA1c), кластеризация записей журнала событий, детекция аномалий в дневнике АД. | Базовый ML на реальных временных рядах. |
| **Сквозной: Git и процесс** | Весь код — в общем репозитории. Ветки, pull requests, код-ревью друг друга, README, язык как список задач. | Командная разработка, гигиена репозитория. |

## 5. Этапы и сроки (8 недель)

Как делать работу на две ветки: рекомендуем не «один делает бэк, другой фронт», а вести обе полосы параллельно с обменом ревью: например, один несёт блоки 1–3 (данные и калькуляторы), второй — блоки 4–5 (LLM и дашборд), при этом каждый делает код-ревью PR'ов другого. Блок 0 делаете вместе — общее понимание домена критично.

| Неделя | Этап | Результат (артефакт) |
| :---: | :--- | :--- |
| **1** | Погружение: разбор предметной области (что такое МИС, ЭМК, МКБ-10), настройка окружения, git, разбор JSON (блок 0) | Репозиторий, карта структуры JSON, словарь полей |
| **2–3** | Парсер и нормализация (блок 1), извлечение из текста регулярками (блок 2) | Модуль parser/ с тестами; чистый датасет |
| **3–4** | Калькуляторы и красные флаги (блок 3) | Модуль calculators/ с юнит-тестами; список сработавших флагов по пациенту |
| **4–5** | LLM-суммаризация (блок 4) | Модуль summarizer/; примеры сводок; промпты в репозитории |
| **5–7** | Дашборд (блок 5), интеграция всех блоков | Работающее веб-приложение |
| **7–8** | Полировка, проверка на втором JSON-примере, README, подготовка защиты | Демо + презентация 7–10 слайдов |

## 6. Требования и договорённости
* **Язык** — Python 3.10+. **Дашборд** — Streamlit (по умолчанию); можно Dash/FastAPI+фронт, если хочется.
* Код в git-репозитории. Работаем через ветки и pull requests, в main напрямую не пушим. Каждый PR ревьюит второй участник.
* На парсер и калькуляторы — юнит-тесты (pytest). Медицинская формула без теста = формула со слепыми ошибками.
* Секреты (ключи LLM API) не коммитим, прячем в `.env`.
* README: как запустить проект с нуля за 5 минут.
* LLM используем для суммаризации текста, а не для «угадай значение анализа». Всё числовое считаем кодом, детерминировано.

## 7. Критерии готовности (Definition of Done)
* Дашборд запускается одной командой и корректно отрабатывает эталонный JSON и минимум один другой сгенерированный файл.
* Парсер переваривает все форматы дат/чисел и пропуски без падений; дубликаты не искажают графики и сводку.
* Реализовано не менее 5 калькуляторов/правил красных флагов, каждый покрыт тестами.
* LLM-сводка структурирована (диагнозы, терапия, динамика, что важно на ближайшем приёме) и не содержит выдуманных фактов при выборочной проверке.
* Есть презентация с демо и выводами: что было сложного в данных, какие решения приняли.
