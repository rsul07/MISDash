# Инструкция по командной работе (Workflow)

Этот документ коротко объясняет, как мы работаем с Git, пишем код и принимаем изменения в проект.

---

## 1. Работа с ветками

Прямой пуш в `main` запрещен. Ветка `main` всегда должна оставаться рабочей и протестированной.

Вся разработка идет в отдельных feature-ветках. Название ветки делаем в формате `тип/название-задачи` или `тип/номер-issue-название`.

Примеры:
- `feat/parser-dates` — новая фича, например парсер дат.
- `fix/bmi-calc-zero-division` — исправление бага.
- `docs/update-readme` — обновление документации.

Как работаем:
1. Сначала обновляем локальную `main`: `git checkout main` и `git pull`.
2. Создаем новую ветку: `git checkout -b feat/your-feature-name`.
3. Делаем изменения и коммиты.
4. Отправляем ветку в GitHub: `git push origin feat/your-feature-name`.

---

## 2. Именование коммитов

Мы используем **Conventional Commits**. Это помогает быстро понять, что именно изменилось, даже если история коммитов большая.

Формат такой: `тип: короткое описание`.

Основные типы коммитов:
- `feat:` — новый функционал, например калькулятор или график.
- `fix:` — исправление ошибки.
- `docs:` — изменения в документации, например в `README` или `docs/`.
- `test:` — добавление или изменение тестов.
- `refactor:` — переработка кода без изменения поведения.
- `chore:` — технические задачи вроде обновления зависимостей, `.gitignore` или линтеров.

Примеры:
- `feat: add CKD-EPI calculator`
- `fix: handle null values in patient birth date`
- `test: add unit tests for BMI formula`
- `chore: update requirements.txt with streamlit`

---

## 3. Pull Request и code review

Когда задача готова, открываем Pull Request в `main` через GitHub.

Что важно в PR:
1. Даем понятное название и описание. Нужно сразу понять, что делает код, а если есть Issue, добавляем ссылку на него, например `Closes #3`.
2. Назначаем обязательного reviewer из команды.
3. Reviewer проверяет логику, читаемость и тесты. Если есть замечания, он оставляет комментарии, а автор исправляет их новыми коммитами в той же ветке.
4. После `Approve` можно мерджить в `main`. Для истории проекта лучше использовать `Squash and merge`.
5. После мержа ветку удаляем в GitHub.

## 4. Требования проекта

Чтобы медицинский прототип оставался надежным, придерживаемся этих правил.

### Тестирование
- Медицинская формула без теста — это потенциальная ошибка. Все парсеры сложных данных и все медицинские калькуляторы, включая ИМТ, СКФ и индексы, обязательно покрываем юнит-тестами на `pytest`.
- Тесты кладем в папку `tests/`. PR с новым калькулятором без тестов на ревью не пропускается.

### Использование LLM
- LLM используем только для работы со свободным текстом: жалобы, анамнез, заключения исследований, суммаризация и выделение главного.
- Нельзя использовать LLM, чтобы угадывать значения анализов или считать формулы. Вся числовая и доменная логика, включая красные флаги и тренды, пишется детерминированно на Python.

### Секреты и ключи
- Ключи для LLM API и другие секреты никогда не коммитим в репозиторий.
- Все секреты храним локально в файле `.env`; он уже добавлен в `.gitignore`.
- Чтобы команда использовала одинаковые имена переменных, держим файл `.env.example` с названиями переменных без самих ключей.

### Кодстайл
- Пишем на Python 3.10+.
- Обязательно используем type hints, особенно в парсере и дата-классах или Pydantic-моделях, чтобы аккуратнее работать с грязными данными МИС.
